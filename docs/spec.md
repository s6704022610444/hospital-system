# System Specification: Hospital Outpatient Department (OPD) System

## Problem Statement
การให้บริการผู้ป่วยนอก (OPD) ในโรงพยาบาลปัจจุบันมักประสบปัญหาความกระจัดกระจายของข้อมูล ข้อมูลประวัติผู้ป่วย ผลการตรวจทางห้องปฏิบัติการ และรายการยาถูกจัดเก็บแยกส่วนตามแผนก ทำให้บุคลากรต้องกรอกข้อมูลซ้ำซ้อนและขาดภาพรวมข้อมูลผู้ป่วยแบบจุดเดียว (Single Patient View) นอกจากนี้ การติดตามสถานะคิวและการประสานงานข้ามแผนก (เช่น เวชระเบียน พยาบาลคัดกรอง แพทย์ ห้องแล็บ รังสีวินิจฉัย เวชศาสตร์นิวเคลียร์ การเงิน และห้องจ่ายยา) ขาดความโปร่งใสแบบเรียลไทม์ นำไปสู่ปัญหาคนไข้ตกค้าง ยอดหนี้ค้างชำระจากการหนีกลับ (Walkout) การสั่งยาซ้ำซ้อนหรือยาที่ผู้ป่วยแพ้ ตลอดจนการขาดระบบบันทึกหลักฐานการเข้าถึงและแก้ไขข้อมูลสุขภาพ (Audit Trail) ที่รัดกุมตามข้อกำหนดทางกฎหมายเวชระเบียนและ PDPA

## Solution
ระบบโรงพยาบาลผู้ป่วยนอก (OPD Web Application) บนสถาปัตยกรรมคลาวด์ Next.js (TypeScript) ร่วมกับ Supabase (PostgreSQL, Row Level Security, Realtime, และ Auth) ที่รวมศูนย์ข้อมูลผู้ป่วยทั้งหมดไว้ภายใต้รหัสประจำตัวเดียว (Single Patient View ผูกด้วย HN) พร้อมระบบ Dual State Machine จัดการสถานะการเดินทางของผู้ป่วยและวงรอบชีวิตของคำสั่งตรวจแบบเรียลไทม์ รองรับการทำงานของบุคลากร 10 บทบาทด้วยระบบสลับบทบาทการทำงาน (Active Role Switching) ควบคุมความปลอดภัยระดับ Database RLS ร่วมกับระบบป้องกันการเข้าถึงข้อมูลโดยไม่บันทึกประวัติ (Strict RPC Barrier for Read Audit) ระบบควบคุมความปลอดภัยทางคลินิก (Safety Guardrails) สำหรับการแพ้ยาและสารรังสีนิวเคลียร์ พร้อมระบบตัดสต็อกยาแบบ 2 จังหวะเพื่อป้องกันยาขาดหน้างาน

## User Stories

### เวชระเบียน (Registrar)
1. ในฐานะเจ้าหน้าที่เวชระเบียน ฉันต้องการลงทะเบียนผู้ป่วยใหม่พร้อมระบุเลขบัตรประชาชน 13 หลัก เพื่อสร้างเลขประจำตัวผู้ป่วย (HN) ถาวรโดยไม่เกิดความซ้ำซ้อน
2. ในฐานะเจ้าหน้าที่เวชระเบียน ฉันต้องการใช้ระบบจำลองการอ่านบัตร Smart Card (Simulated Health ID) เพื่อดึงข้อมูลประวัติส่วนตัวและสิทธิการรักษาของผู้ป่วยเข้ามาในแบบฟอร์มลงทะเบียนโดยอัตโนมัติ
3. ในฐานะเจ้าหน้าที่เวชระเบียน ฉันต้องการเปิดการเข้ารับบริการ (Visit/VN) สำหรับผู้ป่วยที่มารับบริการในวันนั้น เพื่อส่งตัวผู้ป่วยเข้าสู่คิวคัดกรองพยาบาล
4. ในฐานะเจ้าหน้าที่เวชระเบียน ฉันต้องการเห็นการแจ้งเตือนสีแดงเด่นชัด (Outstanding Balance Alert) ทันทีที่ค้นหาผู้ป่วยที่มียอดหนี้ค้างชำระจากการรับบริการครั้งก่อน เพื่อแจ้งให้ผู้ป่วยไปชำระหนี้ค้างชำระก่อนเข้าตรวจ
5. ในฐานะเจ้าหน้าที่เวชระเบียน ฉันต้องการดูหน้าจอคิวผู้ป่วยที่รอการลงทะเบียนและเปิด Visit แบบเรียลไทม์ เพื่อบริหารจัดการแถวรอคอยได้อย่างรวดเร็ว

### พยาบาลคัดกรอง (Nurse)
6. ในฐานะพยาบาลคัดกรอง ฉันต้องการดูรายชื่อผู้ป่วยที่ลงทะเบียนเปิดสิทธิ์แล้วในคิวคัดกรองแบบเรียลไทม์ เพื่อเรียกผู้ป่วยเข้ารับการประเมินสัญญาณชีพ
7. ในฐานะพยาบาลคัดกรอง ฉันต้องการบันทึกสัญญาณชีพ (Vital Signs เช่น ความดันโลหิต ชีพจร อุณหภูมิ อัตราการหายใจ น้ำหนัก ส่วนสูง) พร้อมคำนวณ BMI อัตโนมัติ เพื่อส่งต่อให้แพทย์ประกอบการวินิจฉัย
8. ในฐานะพยาบาลคัดกรอง ฉันต้องการบันทึกอาการสำคัญ (Chief Complaint) และประวัติการเจ็บป่วยปัจจุบัน เพื่อให้แพทย์ทราบเหตุผลการมารับบริการ
9. ในฐานะพยาบาลคัดกรอง ฉันต้องการบันทึกประวัติการแพ้ยา อาหาร หรือสารเคมี พร้อมระบุระดับความรุนแรงและอาการแพ้ เพื่อให้ระบบใช้ตรวจสอบและเตือนแพทย์ขณะสั่งยา
10. ในฐานะพยาบาลคัดกรอง ฉันต้องการกดส่งผู้ป่วยที่คัดกรองเสร็จแล้วเข้าสู่คิวตรวจของห้องแพทย์ เพื่อให้สถานะของผู้ป่วยเปลี่ยนเป็นรอตรวจ (`triaged`) โดยอัตโนมัติ

### แพทย์ (Doctor)
11. ในฐานะแพทย์ ฉันต้องการเห็นคิวตรวจผู้ป่วยที่แยกชัดเจนระหว่างผู้ป่วยใหม่ที่รอตรวจครั้งแรก กับผู้ป่วยที่ตรวจหัตถการเสร็จแล้วและวนกลับมาฟังผล (`doctor_review`) เพื่อจัดลำดับความเร่งด่วนในการตรวจได้อย่างถูกต้อง
12. ในฐานะแพทย์ ฉันต้องการกดเรียกผู้ป่วยเข้าห้องตรวจ เพื่อให้สถานะผู้ป่วยเปลี่ยนเป็นกำลังตรวจ (`in_doctor`) และหน้าจอคิวภายนอกสะท้อนสถานะปัจจุบัน
13. ในฐานะแพทย์ ฉันต้องการเปิดดู Single Patient View ซึ่งรวมประวัติการรักษาเก่า สัญญาณชีพ ผลแล็บ ผลตรวจทางรังสี และประวัติการใช้ยาไว้ในหน้าเดียว เพื่อการวินิจฉัยที่แม่นยำ
14. ในฐานะแพทย์ ฉันต้องการบันทึกประวัติการตรวจร่างกายและการวินิจฉัยโรคตามรหัสมาตรฐาน ICD-10 เพื่อใช้เป็นข้อมูลทางการแพทย์และสถิติโรงพยาบาล
15. ในฐานะแพทย์ ฉันต้องการสั่งตรวจทางห้องปฏิบัติการ (Lab Orders) และตรวจทางรังสีวินิจฉัย (X-ray Orders) เพื่อส่งคำสั่งตรวจไปยังแผนกที่เกี่ยวข้องทันที
16. ในฐานะแพทย์ ฉันต้องการสั่งจ่ายยาจากบัญชียาโรงพยาบาล โดยระบบจะแสดงสถานะจำนวนยาคงเหลือจริงในคลัง เพื่อไม่ให้สั่งยาที่หมดสต็อก
17. ในฐานะแพทย์ ฉันต้องการได้รับการแจ้งเตือนสีแดงทันทีเมื่อสั่งยาที่ผู้ป่วยมีประวัติแพ้ และสามารถกรอกเหตุผลความจำเป็นทางคลินิกเพื่อยืนยันการสั่งยาในกรณีพิเศษได้
18. ในฐานะแพทย์ ฉันต้องการให้ระบบทำการจองสต็อกยา (Reserve Stock) อัตโนมัติเมื่อกดบันทึกใบสั่งยา เพื่อป้องกันไม่ให้ยาถูกสั่งตัดหน้าโดยผู้ป่วยรายอื่น
19. ในฐานะแพทย์ ฉันต้องการสั่งตรวจหัตถการเวชศาสตร์นิวเคลียร์ (เช่น I-131 Therapy หรือ Imaging Scan) โดยระบบจะตั้งค่าการชำระเงินเป็น Post-paid ให้อัตโนมัติเพื่อป้องกันความล่าช้าในการเตรียมสารรังสี
20. ในฐานะแพทย์ ฉันต้องการกดส่งผู้ป่วยไปชำระเงินหรือรับยาหลังตรวจเสร็จสิ้น เพื่อขับเคลื่อนสถานะการเดินทางของผู้ป่วยไปยังขั้นตอนถัดไป

### นักเทคนิคการแพทย์ (Medical Technologist / `med_tech`)
21. ในฐานะนักเทคนิคการแพทย์ ฉันต้องการเห็นคิวคำสั่งตรวจแล็บที่ได้รับมอบหมายแบบเรียลไทม์ เพื่อวางแผนการตรวจวิเคราะห์สิ่งส่งตรวจ
22. ในฐานะนักเทคนิคการแพทย์ ฉันต้องการอัปเดตสถานะของคำสั่งตรวจแล็บ (เช่น `in_procedure`, `result_pending`) เพื่อให้แพทย์และพยาบาลทราบความคืบหน้า
23. ในฐานะนักเทคนิคการแพทย์ ฉันต้องการบันทึกผลการตรวจวิเคราะห์ทางห้องปฏิบัติการ พร้อมช่วงค่าอ้างอิงปกติ (Reference Range) เพื่อให้แพทย์ใช้แปลผล
24. ในฐานะนักเทคนิคการแพทย์ ฉันต้องการกดยืนยันการรายงานผลแล็บ (`completed`) เพื่อให้ระบบส่งสัญญาณไปยัง Macro State ของผู้ป่วยโดยอัตโนมัติ

### เจ้าหน้าที่เวชศาสตร์นิวเคลียร์ (Nuclear Medicine Officer / `nuclear_med`)
25. ในฐานะเจ้าหน้าที่เวชศาสตร์นิวเคลียร์ ฉันต้องการเห็นคิวคำสั่งตรวจและหัตถการทางเวชศาสตร์นิวเคลียร์ พร้อมรายละเอียดประเภทการตรวจและปริมาณสารรังสีที่ระบุ
26. ในฐานะเจ้าหน้าที่เวชศาสตร์นิวเคลียร์ ฉันต้องการใช้เครื่องคำนวณการสลายตัวของสารรังสี (Decay Calculator) บนหน้าจอแบบเรียลไทม์ เพื่อช่วยคำนวณปริมาณกัมมันตภาพรังสีที่จะให้ผู้ป่วยตามเวลาจริง
27. ในฐานะเจ้าหน้าที่เวชศาสตร์นิวเคลียร์ ฉันต้องการบันทึกข้อมูลการสอบเทียบและการให้สารรังสีจริง (Calibrated Dose, Administered Dose, วันเวลา และเลข Lot) เก็บเป็นหลักฐานทางกฎหมายลงในระบบ
28. ในฐานะเจ้าหน้าที่เวชศาสตร์นิวเคลียร์ ฉันต้องการให้ระบบบล็อกการเริ่มทำหัตถการอย่างเด็ดขาด (Hard Stop 100%) หากผู้ป่วยหญิงวัยเจริญพันธุ์ยังไม่มีผลตรวจการตั้งครรภ์เป็นลบ (UPT Negative) เพื่อป้องกันอันตรายต่อทารกในครรภ์
29. ในฐานะเจ้าหน้าที่เวชศาสตร์นิวเคลียร์ ฉันต้องการให้ระบบแสดงคำเตือน (Soft Warning) สำหรับข้อกำหนดการเตรียมตัวอื่นๆ (เช่น การงดไอโอดีน การงดให้นมบุตร) และสามารถให้แพทย์เฉพาะทางกด Override พร้อมกรอกเหตุผลทางคลินิกได้
30. ในฐานะเจ้าหน้าที่เวชศาสตร์นิวเคลียร์ ฉันต้องการบันทึกรายงานผลการสแกนและผลการรักษา เพื่อส่งผลกลับไปยังแพทย์เจ้าของไข้

### เจ้าหน้าที่การเงิน (Cashier)
31. ในฐานะเจ้าหน้าที่การเงิน ฉันต้องการเห็นคิวผู้ป่วยที่รอการชำระเงิน ทั้งผู้ป่วยที่ต้องจ่ายค่าตรวจล่วงหน้า (Pre-paid) และผู้ป่วยที่รอชำระเงินรอบสุดท้ายก่อนรับยา
32. ในฐานะเจ้าหน้าที่การเงิน ฉันต้องการเห็นใบแจ้งหนี้รวมยอดเดียว (Consolidated Single Invoice) ที่รวมยอดคำสั่งตรวจ Post-paid ค่ายา และค่าบริการโรงพยาบาลไว้ในที่เดียวกัน โดยจำแนกรายการในสิทธิ์และนอกสิทธิ์อย่างชัดเจน
33. ในฐานะเจ้าหน้าที่การเงิน ฉันต้องการออก Mock PromptPay QR Code เพื่อให้ผู้ป่วยสแกนจ่ายเงินผ่านระบบจำลองการเงิน
34. ในฐานะเจ้าหน้าที่การเงิน ฉันต้องการให้ระบบยืนยันการรับชำระเงินและออกใบเสร็จรับเงินอย่างเป็นทางการ พร้อมส่งสัญญาณให้ระบบตัดสต็อกยาจริง (Deduct) และส่งผู้ป่วยไปยังคิวรับยาโดยอัตโนมัติ
35. ในฐานะเจ้าหน้าที่การเงิน ฉันต้องการดำเนินการยกเลิกใบเสร็จและคืนเงิน (Void / Refund) ในกรณีที่มีการยกเลิกคำสั่งตรวจที่เคยชำระเงินไปแล้ว โดยระบุเหตุผลเพื่อความถูกต้องของบัญชี
36. ในฐานะเจ้าหน้าที่การเงิน ฉันต้องการปรับสถานะผู้ป่วยที่ไม่มาชำระเงินและเดินทางกลับเป็น `unpaid_debt` เพื่อบันทึกยอดหนี้ค้างชำระไว้ในระบบ

### เภสัชกร (Pharmacist)
37. ในฐานะเภสัชกร ฉันต้องการเห็นคิวใบสั่งยาที่ได้รับการชำระเงินเรียบร้อยแล้วแบบเรียลไทม์ เพื่อเริ่มกระบวนการจัดยาและตรวจสอบความถูกต้อง
38. ในฐานะเภสัชกร ฉันต้องการดูรายการยา ขนาดยา วิธีใช้ และคำเตือนการแพ้ยาของผู้ป่วยบนหน้าจอเดียว เพื่อความปลอดภัยในการจ่ายยา
39. ในฐานะเภสัชกร ฉันต้องการกดยืนยันการตรวจสอบและส่งมอบยาให้ผู้ป่วย (`dispensed`) เพื่อเปลี่ยนสถานะการเข้ารับบริการเป็นเสร็จสิ้น (`completed`)

### เจ้าหน้าที่คลังสินค้า (Warehouse)
40. ในฐานะเจ้าหน้าที่คลังสินค้า ฉันต้องการดูยอดสต็อกยาภาพรวมของโรงพยาบาล ซึ่งแสดงยอดคงเหลือจริง ยอดที่ถูกจองไว้ และยอดที่พร้อมจำหน่าย
41. ในฐานะเจ้าหน้าที่คลังสินค้า ฉันต้องการบันทึกการรับยาเข้าคลัง (Stock In) เพื่อเพิ่มจำนวนยาในระบบและปลดบล็อกการสั่งยาของแพทย์
42. ในฐานะเจ้าหน้าที่คลังสินค้า ฉันต้องการดูประวัติความเคลื่อนไหวทางบัญชีสต็อก (Inventory Transactions) ทั้งการจอง การตัดจ่ายจริง และการรับเข้ายา

### ผู้ดูแลระบบ (Admin)
43. ในฐานะผู้ดูแลระบบ ฉันต้องการบริหารจัดการบัญชีผู้ใช้งาน และมอบหมายบทบาทการทำงาน (Roles) ให้แก่บุคลากรแต่ละคนได้มากกว่า 1 บทบาท
44. ในฐานะผู้ดูแลระบบ ฉันต้องการตรวจสอบตาราง Audit Log ทั้งหมดที่บันทึกการเข้าดูข้อมูล (Read Audit) และการเปลี่ยนแปลงข้อมูล (Write Audit) เพื่อสืบค้นความปลอดภัย
45. ในฐานะผู้ดูแลระบบ ฉันต้องการส่งออกข้อมูล Audit Log เป็นไฟล์ CSV โดยระบบจะบันทึกหลักฐานการสั่งส่งออกข้อมูล (Self-Auditing) ไว้เสมอ

### ผู้อำนวยการโรงพยาบาล (Director)
46. ในฐานะผู้อำนวยการ ฉันต้องการดูแดชบอร์ดภาพรวมการดำเนินงานของโรงพยาบาล (Director Dashboard) แสดงจำนวนผู้ป่วยแยกตามแผนก ปริมาณการให้บริการ และระยะเวลารอคอยเฉลี่ย
47. ในฐานะผู้อำนวยการ ฉันต้องการดูแดชบอร์ดสถิติความปลอดภัยและการตรวจสอบ (Security & Audit Metrics) เช่น ความถี่ในการเปิดดูข้อมูลสุขภาพผู้ป่วย และสถิติการสลับบทบาทการทำงานของบุคลากร
48. ในฐานะผู้อำนวยการ ฉันต้องการสลับบทบาทการทำงานระหว่างผู้บริหาร (`director`) และแพทย์ตรวจรักษา (`doctor`) ได้อย่างราบรื่นผ่านปุ่ม Switch Active Role บนหน้าจอ

## Implementation Decisions

### 1. Dual State Machine & Lifecycle Coordination (ADR 0001)
- **Macro State (`visits.status`):** สะท้อนตำแหน่งทางกายภาพของผู้ป่วยในโรงพยาบาล ประกอบด้วย `registered`, `triaged`, `in_doctor`, `pending_payment`, `pending_orders`, `doctor_review`, `dispensing`, `completed`, `unpaid_debt`, `cancelled`
- **Micro State (`orders.status`):** สะท้อนวงรอบชีวิตคำสั่งตรวจแต่ละใบ ประกอบด้วย `ordered`, `scheduled`, `in_prep`, `in_procedure`, `result_pending`, `completed`, `cancelled`
- **State Transition Driver (Hybrid):** กิจกรรมหน้าห้องตรวจแพทย์และพยาบาลเปลี่ยนสถานะด้วย Manual Action ส่วนกิจกรรมการชำระเงินและคำสั่งตรวจเปลี่ยนสถานะอัตโนมัติด้วย PostgreSQL Database Triggers (เช่น เมื่อ Orders ทุกใบเปลี่ยนเป็น `completed` จะทริกเกอร์ให้ Visit เปลี่ยนเป็น `doctor_review` ทันที)

### 2. Strict RPC Barrier for Read Audit & Realtime Segregation (ADR 0002)
- ไม่อนุญาตให้สิทธิ์ `SELECT` ตารางข้อมูลสุขภาพอ่อนไหว (PHI) ได้แก่ `patients`, `vital_signs`, `diagnoses`, `prescriptions`, `order_results`, `clinical_notes` แก่ผู้ใช้งานทั่วไปโดยตรง
- การเข้าถึง Single Patient View ต้องกระทำผ่าน PostgreSQL RPC Function `log_access(p_hn, p_vn, p_reason)` ซึ่งทำงานแบบ `SECURITY DEFINER` เพื่อบังคับบันทึก Read Audit Record ลงในตาราง `access_logs` ก่อนส่งคืนข้อมูลเสมอ
- ตารางคิวสถานะ (`visits`, `orders`) เปิดให้เข้าถึงผ่าน RLS ปกติ และเชื่อมต่อกับ **Supabase Realtime CDC** เพื่อขับเคลื่อนการแสดงผลคิวแบบเรียลไทม์

### 3. Multi-Role Authorization & Active Role Switching (ADR 0003 & ADR 0011)
- รองรับผู้ใช้งาน 10 บทบาท: `registrar`, `nurse`, `doctor`, `med_tech`, `nuclear_med`, `cashier`, `pharmacist`, `warehouse`, `admin`, `director`
- ตาราง `user_roles` เก็บความสัมพันธ์แบบ 1 User ต่อหลาย Roles เป็น Source of Truth
- ใช้ **Supabase Custom Access Token Hook** ฉีด Claim `roles` และ `active_role` เข้าสู่ JWT ของผู้ใช้
- การสลับบทบาทกระทำผ่าน RPC `switch_active_role(p_new_role)` ร่วมกับการสั่ง Refresh Session บน Client เพื่อออก JWT ใหม่
- RLS Policies ทุกตารางประเมินสิทธิ์จาก JWT Claim `(auth.jwt() -> 'app_metadata' ->> 'active_role')` โดยตรงเพื่อความรวดเร็วระดับ Sub-millisecond

### 4. Separation of Diagnostic Orders from Prescriptions (ADR 0004)
- ตาราง `orders` ดูแลคำสั่งตรวจ Lab, X-ray, Nuclear Imaging, และ I-131 โดยเก็บค่าทางเทคนิคในคอลัมน์ `details` (JSONB + GIN Index)
- ตาราง `prescriptions` และ `prescription_items` แยกออกมาต่างหากในรูปแบบ Normalized Relational เพื่อรองรับการระบุขนาดยา ความถี่ การตรวจจับการแพ้ยา และการตัดสต็อก
- คำสั่งตรวจสามารถกดยกเลิกได้เฉพาะเมื่ออยู่ในสถานะ `ordered` หรือ `scheduled` เท่านั้น หากเข้าสู่ขั้นตอนเตรียมการหรือตรวจแล้วจะถูกบล็อกในระดับ Database
- หากยกเลิก Order ที่ชำระเงินล่วงหน้าแล้ว ต้องทำรายการขอ Void / Refund ผ่านเจ้าหน้าที่การเงินเท่านั้น ไม่มีการคืนเงินอัตโนมัติ

### 5. Nuclear Medicine Decay Engine & Safety Guardrails (ADR 0005)
- เครื่องคำนวณ Radioactive Decay คำนวณแบบ Dynamic บน TypeScript UI เพื่อช่วยเจ้าหน้าที่สอบเทียบปริมาณยาก่อนฉีด
- บันทึก Snapshot ทางกฎหมายของปริมาณรังสีที่ฉีดจริง (`calibrated_dose`, `administered_dose`, `calibration_time`, `administered_time`, `decay_factor`) ลงใน `orders.details`
- **Safety Checklist - Pregnancy Test:** กำหนดเป็น **Absolute Hard Stop 100%** สำหรับสตรีวัยเจริญพันธุ์ หากผล UPT ไม่เป็น Negative หรือยังไม่มีผล จะถูกบล็อกไม่ให้เปลี่ยนสถานะเป็น `in_procedure` ในระดับ Database
- **Safety Checklist - ปัจจัยอื่น:** กำหนดเป็น Soft Warning ที่อนุญาตให้แพทย์เฉพาะทางเวชศาสตร์นิวเคลียร์กด Override ได้โดยบังคับกรอก Clinical Justification

### 6. Simulated External Integrations & High-Density Seed Data (ADR 0006)
- สร้าง Mock Services ผ่าน Next.js Route Handlers (`/api/mock/*`):
  - `/api/mock/health-id/scan`: จำลองการเสียบบัตร Smart Card อ่านข้อมูลประจำตัว
  - `/api/mock/payment/generate-qr` และ `/api/mock/payment/webhook`: จำลองการออก PromptPay QR และยิง Callback เงินเข้าจากธนาคาร
  - `/api/mock/telemed/session`: จำลองห้องวิดีโอคอลทางไกล
- พัฒนา **Simulator Control Panel UI** สำหรับกดจำลองเหตุการณ์เสมือนจริงบนหน้าจอ
- จัดเตรียม Seed Script สำหรับสร้างข้อมูลจำลองผู้ป่วย **150–200 รายการ** กระจายตัวครบทุกสถานะคิวจริง มีเคสแพ้ยา เคสนิวเคลียร์ และบัญชีผู้ใช้ทดสอบครบทั้ง 10 บทบาท

### 7. Immutable Audit Trail & 10-Year Retention (ADR 0007)
- ตาราง `audit_logs` (Write Audit) และ `access_logs` (Read Audit) มีคุณสมบัติเป็น **Append-Only 100% (REVOKE UPDATE/DELETE)**
- กำหนดอายุการจัดเก็บข้อมูลขั้นต่ำ 10 ปี โดยไม่มีการ Auto-purge
- การส่งออก Audit Log เป็นไฟล์ CSV จะทริกเกอร์ระบบ **Recursive Self-Auditing** บันทึกเหตุการณ์ `log_export_generated` พร้อมระบุผู้ใช้ วันเวลา และเงื่อนไข Filter เสมอ

### 8. Warehouse Master Inventory & Two-Phase Stock Deduction (ADR 0008)
- ใช้โมเดล **Single Unified Hospital Master Stock** ในตาราง `medications` โดยทุกแผนกตัดยอดจากคลังเดียวกัน
- กลไกการตัดสต็อก 2 จังหวะ:
  - **Phase 1 (Reserve on Order):** เมื่อแพทย์สั่งยา ระบบจะเพิ่มค่า `reserved_stock` เพื่อล็อกยาไว้ทันที
  - **Phase 2 (Deduct on Paid):** เมื่อยืนยันการชำระเงิน ระบบจะลดค่า `total_stock` และ `reserved_stock`
  - หากยกเลิกใบสั่งยา ระบบจะคืนค่า `reserved_stock` กลับสู่สถานะว่าง
- บังคับใช้ **Hard Block ป้องกันสต็อกติดลบ 100%** ผ่าน Database Check Constraints

### 9. Consolidated Final Invoicing & Walkout Debt Management (ADR 0009)
- ตั้งค่าเริ่มต้นของคำสั่งตรวจเคสด่วน (Emergency) และเวชศาสตร์นิวเคลียร์เป็น `post_paid` อัตโนมัติ (Rule-based Auto-approval)
- การออกบิลรอบสุดท้ายจะรวมยอดคำสั่งตรวจ Post-paid ค่ายา และค่าธรรมเนียมโรงพยาบาล ออกเป็นใบแจ้งหนี้รวมยอดเดียว (**Consolidated Single Invoice**)
- ผู้ป่วยที่ไม่ชำระเงินและออกจากโรงพยาบาลจะถูกปรับสถานะเป็น `unpaid_debt` และบันทึกยอดหนี้สะสมไว้ในโปรไฟล์ผู้ป่วย
- ระบบจะแสดงแถบแจ้งเตือนสีแดง (**Outstanding Balance Alert**) บนหน้าจอเวชระเบียนและพยาบาลคัดกรองเมื่อผู้ป่วยรายดังกล่าวกลับมารับบริการในครั้งถัดไป

### 10. Single Patient View Dashboard & System-Wide OCC (ADR 0010)
- หน้าจอแสดงผลผู้ป่วยหน้าเดียว (`/patient/[hn]`) ประกอบด้วย **Modular Widgets** ที่ปรับการจัดวาง ไฮไลต์ข้อมูล และลำดับการแสดงผลตาม `active_role` ของผู้ใช้
- เปิดใช้งาน **Optimistic Concurrency Control (OCC)** ในทุกตารางข้อมูลที่แก้ไขได้ผ่านคอลัมน์ `version` และ `updated_at` เพื่อป้องกัน Dirty Overwrite
- ยกเว้นตาราง `audit_logs` และ `access_logs` จาก OCC เพื่อรักษาความเป็น Append-Only

### 11. Clinical Safety Guardrails & Realtime Resilience (ADR 0012)
- ระบบตรวจสอบการแพ้ยา (**Drug Allergy Alert**) เด้งเตือนสีแดงทันทีเมื่อแพทย์เลือกยาที่ผู้ป่วยมีประวัติแพ้ พร้อมบังคับกรอกเหตุผลทางคลินิกหากเป็นกลุ่มแพ้รุนแรง
- ป้องกันการสร้าง HN ซ้ำซ้อนด้วย **Unique Constraint บน National ID (CID)** หากมีข้อมูลเดิมอยู่แล้วจะเปิด Visit ใหม่ทันที
- ระบบคืนยาที่ถูกจองอัตโนมัติ (**Phantom Stock Auto-Release**) สำหรับใบสั่งยาที่ค้างชำระเกิน 24 ชั่วโมง
- ระบบหน้าจอคิวมี **SWR Polling Fallback** สำรองอัตโนมัติทุกๆ 15 วินาทีหาก WebSocket Realtime หลุดการเชื่อมต่อ

## Testing Decisions

### What Makes a Good Test
การทดสอบต้องมุ่งเน้น **พฤติกรรมภายนอกของระบบ (External Behavior)** ตามความคาดหวังของผู้ใช้งานและข้อกำหนดความปลอดภัย ไม่ทดสอบรายละเอียดภายในของการเขียนโค้ด (Implementation Details) เพื่อให้สามารถ Refactor โค้ดได้โดยไม่ทำให้การทดสอบล้มเหลว การทดสอบต้องมีความชัดเจนในเงื่อนไข Arrange-Act-Assert (AAA) และครอบคลุมทั้ง Happy Path และ Edge Cases ทางคลินิก

### Modules to be Tested (Pre-agreed Seams)
1. **Database & RLS Seam:**
   - ทดสอบสิทธิ์การเข้าถึงข้อมูลของทั้ง 10 บทบาทตาม RLS Matrix ยืนยันว่าแต่ละบทบาทไม่สามารถอ่าน/เขียนตารางต้องห้ามได้
   - ทดสอบ Strict RPC Barrier ยืนยันว่าการ SELECT ตารางคนไข้โดยตรงต้องถูกปฏิเสธ และการเรียกผ่าน `log_access` จะต้องสร้าง Read Audit Record เสมอ
   - ทดสอบ Append-Only Immutability บนตาราง `audit_logs` และ `access_logs` ว่าคำสั่ง UPDATE และ DELETE จะต้องล้มเหลว 100%
   - ทดสอบ Database Constraints: ห้ามสต็อกติดลบ, เลขบัตรประชาชนซ้ำซ้อน, และ Pregnancy Hard Stop ก่อนเข้าทำหัตถการนิวเคลียร์
2. **State Machine & Inventory Trigger Seam:**
   - ทดสอบ Macro State Transitions: การเลื่อนสถานะอัตโนมัติเมื่อ Orders ครบทุกใบเข้าสู่ `doctor_review`
   - ทดสอบ Two-Phase Stock Deduction: ตรวจสอบการเพิ่มขึ้นของ `reserved_stock` ตอนสั่งยา และการตัดยอด `total_stock` เมื่อชำระเงิน ตลอดจนการปลดล็อกคืนเมื่อยกเลิก
3. **Application & API Seam (End-to-End User Flow):**
   - ทดสอบการไหลเวียนของผู้ป่วยตั้งแต่ลงทะเบียน คัดกรอง พบแพทย์ รายงานผลแล็บ ชำระเงิน จนถึงจ่ายยา
   - ทดสอบระบบ Active Role Switching และการปฏิเสธการทำรายการที่ผิดบทบาท
   - ทดสอบ Mock Services: การจำลองสแกนบัตร Health ID และการจำลอง Callback Webhook ยอดชำระเงินจากธนาคาร
   - ทดสอบระบบแจ้งเตือนทางคลินิก: Drug Allergy Pop-up และ Outstanding Debt Alert

### Prior Art
- การเขียน Database Integration Tests บน PostgreSQL Container ร่วมกับ Supabase CLI
- การเขียน E2E & Component Tests ด้วย Vitest, Testing Library, และ Playwright สำหรับการทดสอบ User Journeys และ Role Permissions

## Out of Scope
ข้อกำหนดต่อไปนี้อยู่นอกเหนือขอบเขตการทำงานของเวอร์ชันแรก (V1 Scope):
1. **ระบบผู้ป่วยใน (Inpatient Department - IPD):** ไม่รวมการจัดการเตียง (Bed Management), การรับผู้ป่วยใน (Admission Number - AN), และการบันทึกเวชระเบียนหอผู้ป่วย
2. **ระบบวิดีโอคอลจริง (Live Telemedicine WebRTC):** ไม่รวมการติดตั้งเซิร์ฟเวอร์สื่อสารภาพและเสียงจริง ให้ใช้เป็นระบบจำลอง (Simulated Telemedicine Session)
3. **การเชื่อมต่อภายนอกของจริง (Live Production Integrations):** ไม่รวมการต่อ API ธนาคารจริง, เครื่องอ่านบัตรประชาชนจริง, และระบบส่งเบิกประกันสุขภาพ (สปสช., ประกันสังคม, กรมบัญชีกลาง) ให้ใช้ Mock Services ทั้งหมด
4. **การตีมูลค่าสต็อกสินค้าทางบัญชี (Detailed Stock Valuation):** ไม่รวมการคำนวณต้นทุนยาแบบ FIFO, LIFO, หรือ Weighted Moving Average
5. **การโอนย้ายสินค้าระหว่างคลังย่อย (Sub-inventory Transfers):** ใน V1 ใช้ระบบสต็อกรวมศูนย์จุดเดียว (Single Unified Master Stock)

## Further Notes
- ระบบได้รับการออกแบบให้สามารถพัฒนาและทดสอบแบบครบวงจรบนเครื่อง Local Development (Local Supabase + Next.js) โดยไม่จำเป็นต้องสมัครหรือเชื่อมต่อบริการคลาวด์ภายนอกระหว่างขั้นตอนการพัฒนา
- เมื่อพร้อมสำหรับการ Deploy ขึ้น Production สามารถนำ Schema DDL Script ไปรันบน Supabase Cloud และเชื่อมต่อกับ Vercel ได้ทันทีโดยใช้การตั้งค่า Environment Variables พื้นฐาน
